# 小白报告规范

## 固定顺序

1. **一句话结论**：说清目前正常、异常或证据不足。
2. **检测到的环境**：系统、活动网络、TUN、IPv4/IPv6、节点入口、出口和 Agent 控制通道线索；未知项明确写未知。
3. **可观测链路**：按区段展示成功、失败、延迟和丢包。
4. **异常区段**：只指出证据支持的最小故障范围。
5. **证据**：列出两到三条决定性观察及时间。
6. **推荐下一步**：明确指出最能验证假设的动作；需要用户决定范围或风险时，再给 2–3 个带解释的选项，并把推荐项放在第一位。
7. **无法观测的部分**：说明代理商内部、回程或被过滤跳点等盲区。
8. **进阶解释**：用户需要时再展开协议和内核细节。

## 用词

- 首次使用缩写时同时写中文含义。
- 用“目前证据更支持”代替“肯定是”。
- 用“没有响应”代替“这个端口一定没开”；防火墙丢弃也可能表现为没有响应。
- 用“可观测路径”代替“真实完整线路”。
- 不把重启后恢复等同于已经找到根因。

## 结论等级

- **高置信度**：同一故障在相邻观察点之间被复现，并有协议级结果支持。
- **中置信度**：多项证据一致，但至少有一个关键观察点缺失。
- **低置信度**：仅有单次 traceroute、第三方 IP 标签或用户体感。

报告必须写明置信度，不得为了显得确定而省略限制。

## 报告后的选择

报告已经能确定下一步时，直接推荐该动作，不要为了互动而强行展示菜单。确实存在多个合理方向时，按照 `guided-dialogue.md` 提问：说明为什么需要用户决定、每个选项接下来会做什么，以及哪些内容仍然无法证明。

下一步会改变网络时，先按 `control-channel-safety.md` 给出放行或阻止结论。需要用户人工操作时，不只给按钮或命令，还要同时说明目的、预期结果、异常处理和撤销方式；失联时直接切换到紧急恢复卡。
