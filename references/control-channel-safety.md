# Codex 控制通道安全与紧急恢复

> **发布状态（0.2.0）**：本版本只做只读评估和计划生成，不执行远端写入，也不武装或解除自动回滚。`change apply` / `change rollback` 及其 Python 公共函数无条件 fail-closed。本文中的自动回滚事务是未来实现必须满足的审核设计，不是当前可用功能。

## 为什么这是底层规则

Codex 需要联网才能继续接收消息、调用工具和确认结果。如果 Codex 当前使用的代理应用、TUN、系统代理、DNS、路由、节点或 VPS 正是本次要修改的对象，直接重启或覆盖配置可能让执行者和现场一起失联。

这不是“重新连接一下就好”的普通报错，而是控制通道与被维护的数据通道重合。任何 NetOps 工作流只要可能改变网络，都必须先执行本规则。

## 两条硬规则

1. 未确认 Codex 当前控制通道时，只允许只读扫描、生成计划和解释，不允许执行网络变更。
2. 本版本在任何控制通道状态下都不自动执行。已验证的独立通道和可验证回滚仍是未来执行或工具外人工维护的必要证据；人工恢复说明不能代替这些证据，也不能解除当前发布门禁。

`tmux`、保持 SSH 窗口打开或者在同一个代理应用里准备第二个节点，都不算独立通道。它们可能保住远端进程，但代理应用、TUN 或系统路由一旦失效，Codex 仍然无法继续控制。

## 变更前必须确认什么

按下面顺序建立控制通道依赖图：

```text
Codex
  -> 当前设备的系统代理或 TUN
  -> 实际代理进程和本地端口
  -> 当前节点入口
  -> 承载节点的 VPS
  -> 公网与 Codex 服务
```

至少记录以下事实，未知就明确写“未知”：

- Codex 所在设备和当前接入网络。
- 是否启用了 TUN、系统代理或代理环境变量。
- 当前代理应用和实际工作的配置；只记录名称，不复制凭据。
- Codex 当前是否经过本次要修改的节点或 VPS。
- 本次会触碰本地代理应用、TUN、DNS、路由、防火墙、远端代理服务还是 VPS 网络。
- 是否存在真正独立的备用网络、代理进程、设备或服务商控制台。
- 备份位置、计划 ID、自动回滚等待时间和验证方法。

客户端扫描只能发现代理和 TUN 线索，不能独自证明 Codex 究竟经过哪个节点。必须结合当前客户端状态、受控切换测试或用户确认，不能根据一个公网 IP 强行推断。

## 三种处置结果

| 状态 | 是否允许自动变更 | 处理方式 |
| --- | --- | --- |
| 已验证独立通道 | 本版不允许自动执行 | 可继续生成计划，交由独立获批流程审核 |
| 共享通道，计划声明自动回滚 | 本版不允许自动执行 | timer 字段不是已武装证据；停止在计划阶段 |
| 未知、只有同应用备用节点或仅能人工恢复 | 不允许 | 先建立独立通道，或转为人工维护窗口 |

推荐顺序：

1. 独立设备或独立网络上的管理通道。
2. 不共享进程和配置目录的第二代理内核，旧实例保持运行。
3. 远端 Linux 一次性自动回滚定时器。
4. 用户在场的人工维护窗口，仅作为最后选择。

第二代理内核只适合测试应用代理端口。系统只有一个 TUN 所有者时，不能通过抢占当前 TUN 来测试第二实例。涉及系统 DNS、默认路由、防火墙或 TUN 本身时，应使用手机热点、另一台设备或其他真正独立的管理路径。

## Codex 指导人工操作的固定格式

需要用户点击界面、切换网络或输入命令时，每次只给一个主要动作。每一步必须包含五项：

1. **目的**：为什么现在做这一步。
2. **操作**：具体打开哪个界面、点击哪个开关或运行哪条命令。
3. **预期结果**：用户应该看到什么。
4. **异常处理**：结果不同、按钮不存在或网络断开时怎么办。
5. **撤销方式**：怎样恢复到操作前状态。

操作完成后让用户报告实际结果，再给下一步。不要一次扔给小白十几条命令，也不要让用户自己判断 DNS、MTU、路由或防火墙哪一个是原因。

示例：

```text
目的：确认备用网络不经过当前 TUN。

操作：先不要退出代理软件，只关闭它的 TUN 开关，然后把电脑连接到手机热点。

预期结果：浏览器可以打开一个普通 HTTPS 网站，代理软件仍保留原配置。

异常处理：如果热点已连接但网页仍打不开，先检查系统代理是否还指向已经停止的本地端口；不要删除配置。

撤销方式：重新连接原 Wi-Fi，并把 TUN 开关恢复到操作前状态。

完成后请告诉我：热点是否连接成功、普通 HTTPS 是否能打开、Codex 是否仍在线。
```

## 独立通道的准备步骤

### 使用第二代理进程

1. 保持当前正常代理进程、配置目录、本地端口和 TUN 不变。
2. 为测试实例使用单独的程序进程、配置目录和本地 SOCKS/HTTP 端口。
3. 不让测试实例接管系统代理或 TUN。
4. 只让一个测试命令或测试应用显式连接新端口。
5. 分别验证 DNS、普通 HTTPS、目标服务和实际出口。
6. 测试失败时只停止测试实例，原管理通道继续工作。
7. 全部通过后再制定系统代理或 TUN 的切换计划。

同一代理应用里的两个配置不一定是两个进程。只要重启应用会让两个配置一起消失，就不满足独立要求。

### 使用备用网络或设备

1. 提前确认手机热点或第二条网络本身可以联网。
2. 确认它不依赖待修改的本地 TUN、节点或 VPS。
3. 在备用网络上打开普通 HTTPS，再确认 Codex 可以收发消息。
4. 保持备用网络可用，直到新旧路径验证结束。
5. 不要在同一次变更里同时修改主通道和备用通道。

### 使用 VPS 服务商控制台

1. 在变更前登录服务商后台，确认 Web/串口/VNC 控制台确实能打开。
2. 记录目标 VPS、备份位置和计划 ID，不记录密码或节点凭据。
3. 确认控制台不依赖 VPS 自己的 SSH、代理端口或防火墙放行。
4. 控制台只用于恢复备份、查看定时回滚状态和重启受影响服务，不做无关修改。

## 远端自动回滚设计（本版未发布）

下面记录未来远端变更执行器必须满足的顺序，用于审查计划和实现。当前 `netopsctl` 不会运行这些步骤，也不能创建一次性 systemd transient timer：

1. 预检只能使用类型化只读检查；自由 Shell 不允许放在 `preflight` 阶段。
2. 每个 payload 和 `apply` 操作必须声明绝对文件目标；每个目标都要有同路径的类型化 `file-sha256` 预检，填写只读审计所得的内容与 GNU/Linux 元数据摘要，并且必须是已存在、单硬链接的普通文件而非符号链接，`backup_paths` 还要逐项精确匹配这些目标。父目录 tar、计划执行前不存在的新文件和任意一条 rollback Shell 命令都不能被推导成“可恢复”。
3. 完成只读预检后，执行器逐个确认目标仍是普通文件，记录变更前 SHA-256 清单，再只归档这些精确文件；配置备份完成后才写入本计划的回滚脚本。
4. 计划根据 apply、payload、validate、verify 和重启的最大耗时计算最低保护窗口；定时器必须在 120–3600 秒范围内且不短于该窗口。
5. 创建一次性 timer，确认 `.timer` 处于 active，并在状态锁内写入 `change.started` 后，才允许第一个声明的写操作。
6. 应用最小变更，验证配置、服务、入口、出口和旧路径。
7. 全部通过后在同一个状态锁内停止 `.timer` 和可能已启动的 `.service`，确认两者 inactive，再把状态写成 `disarmed`。
8. 如果 SSH 或 Codex 中断，VPS 不等待新的控制命令，时间到后在状态锁内恢复备份、执行 rollback，核对每个目标与变更前 SHA-256 清单一致，再执行 rollback_verify 并写入最终状态。

每次应用都会生成独立 execution ID，并把备份放在对应计划 ID 下的独立目录。每次执行还必须使用一个不存在的新回执路径；默认回执已经存在时会拒绝重试，避免覆盖上一次的恢复状态。人工回滚必须使用回执中记录的完整备份目录。

如果执行结果显示 `rollback-pending`，不要立即重复运行变更。先等待计划中声明的回滚时间，再通过独立通道、服务商控制台或恢复后的 SSH 检查 `automatic-rollback.status`。

这个机制只保护远端 Linux 变更，不能恢复本机已经损坏的 TUN、系统代理或默认路由。本地变更仍需要独立网络或独立设备。

Transient timer 不会跨 VPS 重启保留。包含重启、关机、替换 init/systemd 或可能让主机重新启动的计划，不能只靠这个定时器放行，必须使用独立管理通道和提前验证的服务商控制台。

`netopsctl safety assess` 是初步判断工具。`netopsctl change plan` 可以生成绑定到计划 ID 的 `rollback_contract` 与 `control_channel_guard`，但这些字段只供审核，不会放行当前版本的执行入口。证据项必须是 8–500 个可打印字符的非秘密审计说明，最多 20 项。

## 常见问题与处理

### 切换节点后所有应用都断网

可能原因：系统代理仍指向已经停止的本地端口，或者 TUN 已退出但路由没有恢复。

处理：不要卸载代理应用。先关闭测试 TUN，检查系统代理开关，再连接备用网络并测试普通 HTTPS。恢复后只启动最后一次确认可用的配置。

### 备用节点也一起失效

可能原因：两个节点属于同一个代理应用、同一个内核进程或同一个 TUN，应用重启时一起中断。

处理：把备用通道改为独立进程、独立设备或独立网络。节点名称不同不等于控制路径独立。

### SSH 窗口还在，但 Codex 已经断线

可能原因：远端 Shell 仍存活，但 Codex 到服务端的本地代理路径已经断开。

处理：让已经武装的远端定时器完成；本地先恢复网络和 Codex，不要把 `tmux` 当作回滚方案。

### 热点连接成功，网页仍打不开

可能原因：系统代理仍指向失效端口、TUN 路由仍在，或者热点本身没有公网连接。

处理：先关闭测试 TUN和残留系统代理；用不经过代理的普通 HTTPS 验证热点。仍失败时换另一台设备确认热点是否正常。

### 新配置能启动，但 Codex 仍无法连接

可能原因：普通网站可用不代表 Codex 所需路径可用；DNS、TLS、IPv6、分流规则或目标域名可能仍走错出口。

处理：保留旧通道，使用新通道分别检查 DNS、TCP/TLS 和普通 HTTPS。不要在尚未证明 Codex 可用时解除回滚定时器。

### 自动回滚定时器没有 active

可能原因：目标机不是 systemd、权限不足、`systemd-run` 不存在或同名计划仍在运行。

处理：停止变更。不要用后台 `sleep` 临时冒充已验证定时器；改用独立管理通道，或在人工维护窗口内先解决调度能力。

### 自动回滚已经触发

处理：不要继续向新配置追加修改。先检查状态文件、旧服务和旧路径是否恢复，再根据原计划生成新的诊断和新的计划 ID。

## 紧急避险卡：先恢复 Codex

紧急状态的目标不是立刻查清根因，而是恢复一条已知可用的控制通道。

1. 停止继续修改，不删除配置、备份、日志或计划文件。
2. 记下故障时间、最后完成的步骤、计划 ID、备份位置和自动回滚等待时间。
3. 关闭正在测试的 TUN 或系统代理，但先不要卸载代理软件。
4. 切换到不经过故障路径的网络，优先手机热点或另一台设备。
5. 用浏览器确认普通 HTTPS 可以打开。
6. 如果所在网络必须使用代理，只启动最后一次确认可用的独立代理配置。
7. 网络恢复后重新启动 Codex；不要先重做刚才的变更。
8. 把下面的“恢复信息卡”交给 Codex，让它从现场状态继续，而不是凭记忆重复执行。

### macOS

1. 在代理应用中只关闭测试中的 TUN/系统代理开关，保留配置。
2. 打开“系统设置 -> 网络 -> 当前网络 -> 详细信息 -> 代理”。
3. 关闭仍指向失效本地端口的网页代理、安全网页代理和 SOCKS 代理。
4. 连接手机热点，使用浏览器验证普通 HTTPS。
5. `scutil --proxy` 只能用于只读核对当前系统代理，不要在慌乱时批量执行网络重置命令。
6. 网络正常后退出并重新打开 Codex。

### Windows

1. 在代理应用中关闭测试 TUN，不删除订阅和配置。
2. 打开“设置 -> 网络和 Internet -> 代理”。
3. 关闭仍指向失效本地端口的“使用代理服务器”；保留原参数截图或记录以便撤销。
4. 连接手机热点，使用浏览器验证普通 HTTPS。
5. 只启动最后一次确认可用的代理配置，再重新打开 Codex。
6. 不要把 `netsh winsock reset`、全量路由清空或重装网卡作为第一步；这些操作会扩大现场变化并可能要求重启。

### Linux 桌面

1. 关闭测试 TUN，保留代理配置和日志。
2. 在桌面网络设置中关闭失效的手动系统代理。
3. 新终端中检查 `HTTP_PROXY`、`HTTPS_PROXY` 和 `ALL_PROXY`；只在当前终端取消错误变量，不修改全局启动文件。
4. 连接独立网络并验证普通 HTTPS，然后重新启动 Codex。
5. 不要在远程 SSH 会话中随意重启 NetworkManager、systemd-networkd 或整机网络。

### VPS 或节点已经失联

1. 如果自动回滚已武装，等待声明的时间，不要重复执行同一计划。
2. 从独立网络测试 SSH 和旧节点是否恢复。
3. 仍未恢复时进入变更前已经验证的服务商控制台。
4. 检查计划备份目录和 `automatic-rollback.status`，不要凭文件时间猜测结果。
5. 只恢复该计划列出的备份并重启受影响服务，然后复核 SSH、面板和旧节点。
6. 控制台也不可用时，停止尝试高风险命令，联系服务商保留磁盘和控制台现场。

## 恢复信息卡

重新启动 Codex 或新建任务时提供以下信息，不包含密码、Token、节点链接、UUID 或私钥：

```text
事件时间：
操作设备和系统：
原来的正常网络/代理配置名称：
本次修改对象：
最后一个确认成功的步骤：
出现断线前执行的动作：
当前普通 HTTPS 是否可用：
当前 Codex 是否可收发消息：
计划 ID：
备份位置：
自动回滚是否已武装、等待多久：
服务商控制台是否可用：
请勿重复的操作：
```

## 外部脚本的额外限制

任何第三方脚本只要可能重启代理、修改防火墙、DNS、默认路由、网络服务、TUN 或内核参数，都属于控制通道风险面。运行前必须：

1. 查看脚本来源、固定版本和实际变更内容。
2. 明确它会重启哪些服务、改哪些文件、是否有非交互安装行为。
3. 经过同一个控制通道判断，不因脚本“知名”而绕过。
4. 能只读运行时先只读；无法限制变更范围时不在活动控制通道上运行。

## 兼容与来源

- 远端自动回滚尚未发布；未来实现若恢复，目标范围仍只考虑使用 systemd 且具备 `systemd-run` 和 `timeout` 的 Linux 主机，并需重新完成目标机预检与对抗审查。
- systemd 的 `--on-active=` 会创建 transient timer，由服务管理器在 SSH 断开后继续管理；成功提交后通过停止对应 `.timer` 解除。
