# 紧急恢复：先把 Codex 救回来

> 本文件只在**已经出问题之后**使用。变更前的门禁、依赖判断和执行合同在 `control-channel-safety.md`，不要为了做一次普通变更而加载本文件。

紧急状态的目标不是立刻查清根因，而是恢复一条已知可用的控制通道。根因等联网恢复后再查。

## 变更前先把恢复信息落到本地文件

断线时聊天窗口可能已经不可用，而计划 ID、备份位置和自动回滚等待时间只在那里出现过。因此高风险变更执行前，Codex 必须把下面的“恢复信息卡”写入用户本机一个固定路径的纯文本文件（例如桌面或下载目录），并把路径告诉用户。

该文件不包含密码、Token、节点链接、UUID 或私钥，只包含恢复所需的非秘密外键。用户完全断网、会话丢失时，仍然可以离线读到它。

```text
事件时间：
操作设备和系统：
原来的正常网络/代理配置名称：
本次修改对象：
最后一个确认成功的步骤：
出现断线前执行的动作：
当前普通 HTTPS 是否可用：
当前 Codex 是否可收发消息：
变更摘要或计划 ID：
备份位置：
自动回滚是否已武装、等待多久：
服务商控制台是否可用：
请勿重复的操作：
```

`netopsctl change apply` 的回执也会落在计划目录下，回执路径同样应当写进这张卡。

## 紧急避险卡

1. 停止继续修改，不删除配置、备份、日志或计划文件。
2. 记下故障时间、最后完成的步骤、变更摘要或计划 ID、备份位置和自动回滚等待时间；变更前已写入的恢复信息卡文件里应该都有。
3. 关闭正在测试的 TUN 或系统代理，但先不要卸载代理软件。
4. 切换到不经过故障路径的网络，优先手机热点或另一台设备。
5. 用浏览器确认普通 HTTPS 可以打开。
6. 如果所在网络必须使用代理，只启动最后一次确认可用的独立代理配置。
7. 网络恢复后重新启动 Codex；不要先重做刚才的变更。
8. 把恢复信息卡交给 Codex，让它从现场状态继续，而不是凭记忆重复执行。

### macOS

1. 在代理应用中只关闭测试中的 TUN/系统代理开关，保留配置。
2. 打开“系统设置 -> 网络 -> 当前网络 -> 详细信息 -> 代理”。
3. 关闭仍指向失效本地端口的网页代理、安全网页代理和 SOCKS 代理。
4. 连接手机热点，使用浏览器验证普通 HTTPS。
5. `scutil --proxy` 只能用于只读核对当前系统代理，不要在慌乱时批量执行网络重置命令。
6. 网络正常后退出并重新打开 Codex。

### Windows

1. 在代理应用中关闭测试 TUN，不删除订阅和配置。
2. 打开“设置 -> 网络和 Internet -> 代理”。
3. 关闭仍指向失效本地端口的“使用代理服务器”；保留原参数截图或记录以便撤销。
4. 连接手机热点，使用浏览器验证普通 HTTPS。
5. 只启动最后一次确认可用的代理配置，再重新打开 Codex。
6. 不要把 `netsh winsock reset`、全量路由清空或重装网卡作为第一步；这些操作会扩大现场变化并可能要求重启。

### Linux 桌面

1. 关闭测试 TUN，保留代理配置和日志。
2. 在桌面网络设置中关闭失效的手动系统代理。
3. 新终端中检查 `HTTP_PROXY`、`HTTPS_PROXY` 和 `ALL_PROXY`；只在当前终端取消错误变量，不修改全局启动文件。
4. 连接独立网络并验证普通 HTTPS，然后重新启动 Codex。
5. 不要在远程 SSH 会话中随意重启 NetworkManager、systemd-networkd 或整机网络。

### VPS 或节点已经失联

1. 如果自动回滚已武装，等待声明的时间，不要重复执行同一计划。
2. 从独立网络测试 SSH 和旧节点是否恢复。
3. 仍未恢复时进入变更前已经验证的服务商控制台。
4. 检查计划备份目录和 `automatic-rollback.status`，不要凭文件时间猜测结果。
5. 只恢复该计划列出的备份并重启受影响服务，然后复核 SSH、面板和旧节点。
6. 控制台也不可用时，停止尝试高风险命令，联系服务商保留磁盘和控制台现场。

## 常见故障与处理

### 切换节点后所有应用都断网

可能原因：系统代理仍指向已经停止的本地端口，或者 TUN 已退出但路由没有恢复。

处理：不要卸载代理应用。先关闭测试 TUN，检查系统代理开关，再连接备用网络并测试普通 HTTPS。恢复后只启动最后一次确认可用的配置。

### 备用节点也一起失效

可能原因：两个节点属于同一个代理应用、同一个内核进程或同一个 TUN，应用重启时一起中断。

处理：把备用通道改为独立进程、独立设备或独立网络。节点名称不同不等于控制路径独立。

### SSH 窗口还在，但 Codex 已经断线

可能原因：远端 Shell 仍存活，但 Codex 到服务端的本地代理路径已经断开。

处理：让已经武装的远端定时器完成；本地先恢复网络和 Codex，不要把 `tmux` 当作回滚方案。

### 热点连接成功，网页仍打不开

可能原因：系统代理仍指向失效端口、TUN 路由仍在，或者热点本身没有公网连接。

处理：先关闭测试 TUN 和残留系统代理；用不经过代理的普通 HTTPS 验证热点。仍失败时换另一台设备确认热点是否正常。

### 新配置能启动，但 Codex 仍无法连接

可能原因：普通网站可用不代表 Codex 所需路径可用；DNS、TLS、IPv6、分流规则或目标域名可能仍走错出口。

处理：保留旧通道，使用新通道分别检查 DNS、TCP/TLS 和普通 HTTPS。不要在尚未证明 Codex 可用时解除回滚定时器。

### 自动回滚定时器没有 active

可能原因：目标机不是 systemd、权限不足、`systemd-run` 不存在或同名计划仍在运行。

处理：停止变更。不要用后台 `sleep` 临时冒充已验证定时器；改用独立管理通道，或在人工维护窗口内先解决调度能力。

### 自动回滚已经触发

处理：不要继续向新配置追加修改。先检查状态文件、旧服务和旧路径是否恢复，再根据原 SSH 事务或计划生成新的诊断和新的变更摘要。
