# 目标网站仅在某个出口拒绝

## 参数化环境

- 直连或出口 A：目标可访问
- 上游出口 B：目标超时、拒绝或支付流程失败
- 其他网站：大多正常

## 用户看到的现象

只有某一类目标在某一个出口上失败：网页转圈后超时、返回明显的拒绝页面，或支付与登录在最后一步被拒。换回另一个出口立刻正常。

## 对照测试

固定目标地址、端口和协议，从 VPS 原生出口和上游出口各做一次可重复探测。再横向扩展：同一出口下换几个不同目标，判断是「这个出口对所有目标都差」还是「只有这个目标拒绝这个出口」。

## 支持和反对每个解释的证据

- 支持「出口 IP 被目标侧分类」：同一出口访问多数网站正常，只有该目标拒绝；DNS 与 TCP/TLS 全部成功，失败发生在 HTTP 层或业务层。
- 支持「链路或端口策略」：TCP 握手就失败，或只有特定端口不通，而其他端口在同一出口正常。
- 反对「供应商封端口」：其他端口和其他目标在同一出口正常，说明不是端口策略。
- 反对「目标封 IP」：换一个同段出口仍被拒，或未登录时可访问而登录后被拒，说明更像账号侧风控。
- 支付失败必须与账号状态、Cookie、地区一致性和登录风险分开验证，不能直接归因于出口。

## 现有证据能确认的故障范围

这组对照能确认「问题在出口 B 之后」，并能区分失败发生在 DNS、TCP/TLS 还是 HTTP 与业务层。它不能单独证明是代理供应商封端口，也不能证明是目标网站封 IP。

## 不能从这份案例推广出去的结论

- 不能推广成「换个出口就修好了」：换出口只是绕开，不解释原因，下一个出口可能几天后进入同一分类。
- 不能推广成「IP 信誉查询能定性」：信誉数据库是第三方线索，不是目标网站的实际判定依据。

## 推荐下一步

从 VPS 原生出口和上游出口对同一目标地址、端口和协议执行一次可重复探测，并依次比较 DNS 答案、TCP/TLS、HTTP 状态、目标端口和 IPv4/IPv6 表现。
